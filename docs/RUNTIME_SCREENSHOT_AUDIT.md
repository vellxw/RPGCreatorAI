# Runtime Screenshot Audit Workflow

Date: 2026-06-04

Issue: CP-098 / FRA-133

## Purpose

Define a repeatable, evidence-based screenshot audit workflow for the native
C++ runtime. This document ensures every runtime menu, dialogue, battle, shop,
save/load, and map scene has documented visual evidence, every visual regression
has a discovery path, and every audit follows the same checklist so runtime
quality remains consistent across phases.

This workflow integrates with:

- `docs/EDITOR_SCREENSHOT_AUDIT.md` — editor-side screenshot audit (CP-097).
- `docs/GAME_VISUAL_QA.md` — visual QA rubric for authored game scenes.
- `docs/RUNTIME_UI_DESIGN.md` — runtime UI layout and interaction source of truth.
- `docs/EDITOR_RUNTIME_E2E_QA.md` — editor-to-runtime roundtrip validation.
- `docs/VALIDATION_LOG.md` — timestamped validation log.
- `docs/screenshots/` — committed evidence storage.

## When to Capture Screenshots

Screenshots are **required** at these trigger points:

| Trigger | Scope | Required? |
| --- | --- | --- |
| Runtime UI layout or styling change | All affected menu/shop/battle/dialogue screens | Yes |
| New runtime menu or sub-screen added | The new screen plus adjacent screens affected | Yes |
| BitmapFont or text rendering change | All text-heavy screens (inventory, party, quests, shop) | Yes |
| Panel color or border change | All panel-based screens | Yes |
| Battle system logic change | Battle turn log, victory, defeat screens | Yes |
| Shop transaction logic change | Shop buy, unaffordable, unavailable states | Yes |
| Save/load format or feedback change | Save/load picker, feedback messages | Yes |
| Dialogue system change | Dialogue text rendering, speaker display | Yes |
| Entity rendering or priority change | Foreground occlusion, Y-sort, entity visibility | Yes |
| Map rendering or tile drawing change | Initial map, map transfer, tile rendering | Yes |
| Phase boundary (milestone close) | Full audit sweep | Yes |
| Integration gate | Full audit of all runtime scenes | Yes |
| Bug fix affecting runtime visuals | The fixed scene before and after | Recommended |

## Audit Checklist

For each screenshot, verify these checks:

### Text Fit

- [ ] All text is fully visible within panel boundaries.
- [ ] No text is clipped, truncated, or overlapping adjacent lines.
- [ ] Long item/quest/actor names do not overflow their allocated space.
- [ ] Numeric values (HP, gold, amounts) are right-aligned or consistently positioned.
- [ ] Font rendering is crisp at the default 800x600 resolution.

### Composition

- [ ] UI panels are centered horizontally as specified in `RUNTIME_UI_DESIGN.md`.
- [ ] Full-screen overlays (menu, shop, battle) maintain the 32px margin.
- [ ] Dialogue strip occupies the expected bottom 120px region.
- [ ] Selection markers (`>`) are visually aligned with row text.
- [ ] HP bars are proportionally correct and do not overflow panel bounds.

### Entity Occlusion

- [ ] Player renders below foreground tiles when standing under them.
- [ ] Events render at the correct priority (below/same/above characters).
- [ ] Y-sort interleaving is correct (entities sorted by visual foot Y).
- [ ] Foreground pass draws after same-priority entities.

### Viewport Framing

- [ ] Map fills the 800x600 viewport without exposed voids at default camera position.
- [ ] Camera clamps correctly at map edges.
- [ ] UI panels do not extend beyond the viewport bounds.
- [ ] Battle, shop, and menu overlays are fully visible within the viewport.

### Color and Styling

- [ ] Panel fill uses the correct translucent black (`kPanelFill`).
- [ ] Panel borders are visible light grey (`kPanelBorder`).
- [ ] Header text uses accent yellow (`kPanelHeader`).
- [ ] Body text uses off-white (`kPanelText`).
- [ ] Disabled/hint text uses dim grey (`kPanelDim`).
- [ ] Success indicators use green (`kPanelOK`), failure uses red (`kPanelBad`).

### State Correctness

- [ ] Save slots show correct map, gold, party, and date metadata.
- [ ] Load empty slots are disabled and show "empty" state.
- [ ] Chest already-opened state reflects self-switch persistence.
- [ ] Battle turn log entries match the deterministic resolver output.
- [ ] Shop affordability markers match actual gold at time of screenshot.
- [ ] Quest objectives show correct `[x]`/`[ ]` completion state.

### Responsive / Scaling

- [ ] Text remains readable when the window is scaled beyond 800x600.
- [ ] Panels scale proportionally with the renderer's scaling factor.
- [ ] No rendering artifacts appear at common window sizes (800x600, 1280x720, 1920x1080).

## Evidence Storage

All runtime screenshot evidence is stored under `docs/screenshots/` following
this naming convention:

```
docs/screenshots/{phase-or-issue-id}/
```

Examples:

- `docs/screenshots/phase-7/` — Phase 7 runtime smoke evidence (18 screenshots).
- `docs/screenshots/phase10-mvp/` — Phase 10 MVP runtime smoke (3 screenshots).
- `docs/screenshots/{future-runtime-audit-id}/` — dedicated evidence for a
  future runtime visual audit that captures a new screenshot set.

Runtime screenshots use `.bmp` format by convention (native SDL renderer output).
Editor-side or browser-captured evidence may use `.png`.

Each audit run produces:

1. **BMP/PNG screenshots** — one file per required screenshot ID.
2. **Smoke script output** — captured stdout from `scripts/dev/smoke-runtime.ps1`
   showing assertion pass/fail for each marker.
3. **Audit report** — a summary appended to this document or the relevant
   phase gate doc.

## Smoke Script Alignment

The runtime smoke script `scripts/dev/smoke-runtime.ps1` already captures
screenshots and asserts runtime log markers. This audit workflow extends that
coverage:

| Smoke assertion | Audit screenshot(s) |
| --- | --- |
| `showChoices` selection logged | R-07, R-08 |
| Event-target movement logged | R-05 |
| `Audio requested: chest_open` | R-09 |
| `pluginCommand debug.log` | (any scene with plugin command) |
| `Smoke shots complete` | all R-series screenshots |

When adding new audit screenshots, update the smoke script to assert the
corresponding runtime log markers so automated and visual evidence stay aligned.

## Follow-Up Issue Filing

When the audit discovers a defect:

1. **Classify severity:**

   | Severity | Description | Action |
   | --- | --- | --- |
   | **Blocking** | Runtime crash, text unreadable, menu unusable | File issue immediately, priority High/Urgent |
   | **Visible defect** | Text overflow, wrong color, incorrect state | File issue, priority Medium |
   | **Minor polish** | Inconsistent spacing, edge-case truncation | File issue, priority Low or batch with next polish pass |

2. **File the issue with evidence:**

   - Title: `[Runtime Visual QA] {scene} — {defect description}`
   - Attach the BMP screenshot showing the defect.
   - Reference the audit checklist ID (e.g., "R-31 battle progress text clipped").
   - Include the window resolution, OS, and reproduction steps.
   - Apply labels: `visual-qa`, `audit`, `runtime`, `phase-11`.

3. **Link to the audit:**

   - Reference this audit doc.
   - Reference the screenshot ID from the required screenshots table.

4. **Do not batch-close:**

   - Follow AGENTS.md Linear discipline: one issue = one fix = one commit.
   - Each defect gets its own validation evidence.

## Audit Execution Steps

To perform a full runtime audit:

1. **Build the native runtime:**

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/dev/verify.ps1 -SkipSmoke
   ```

2. **Run the runtime smoke with screenshots:**

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/dev/smoke-runtime.ps1
   ```

3. **Alternatively, launch the runtime manually** with `--smoke-shots` to
   capture specific scenes:

   ```powershell
   & "$env:LOCALAPPDATA\RPGCreatorAI\build\rpg_creator_runtime.exe" --smoke-shots docs\screenshots\{issue-id}
   ```

4. **Inspect each screenshot** against the audit checklist.

5. **Record findings** — pass or fail each checklist item per screenshot.

6. **File follow-up issues** for any failures.

7. **Append results** to `docs/VALIDATION_LOG.md`.

8. **Commit evidence** with the audit doc changes.
